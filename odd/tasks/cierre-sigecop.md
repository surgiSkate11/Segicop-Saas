## Specs

- S1 — Least privilege everywhere (L1): "Presta especial atención al registro de empresas y usuarios, al envío de credenciales por correo y a la asignación de permisos." "No inventes reglas de negocio ni habilites permisos por defecto sin justificación." Requirements role table: "Mínimo privilegio. Cada rol ve únicamente los datos necesarios para cumplir su función." "Seguridad o garita — Consulta habilitación y registra accesos. — No abre certificados de antecedentes ni expedientes sensibles." "AC-002 Un gestor no puede ver ni modificar otra empresa contratista." "AC-003 Garita ve habilitación y razón operativa sin abrir antecedentes."
- S2 — Role → action matrix is exactly the table in `odd/preguntas-director.md` P5 (derived only from the requirement role descriptions). Anything not in the table is denied. It lives in ONE module so a director answer changes one line.
- S3 — Deny by default: every internal view (empresas, personas, cumplimiento, accesos, trabajos, core alertas/export, identidad panel) checks the action for the user's organizations; without the role the response is HTTP 403 and nothing is written (no rows, no events). Multi-tenant filtering stays explicit (constitution §2.6). Antecedentes keeps its own `permisos.py` rules unchanged. Portal accounts keep `AccesoPortalMiddleware` unchanged.
- S4 — Navigation shows only the entries the user may use; hiding is cosmetic, the 403 is the real control.
- S5 — Gestor scope "solo sus empresas" (AlcanceAsignado) is NOT part of T1; T1 applies org-wide and documents the gap (T3).
- S6 — Tests per role through the HTTP interface (status code, and that a denied POST leaves stored data and event counts unchanged); existing behavior for allowed roles keeps passing.

- S7 — Internal users (T2): only `gestionar_usuarios` (admin_cliente) lists, invites, resends and deactivates internal users of its organizations. Assignable roles are exactly the matrix roles (`ROLES_INTERNOS`), never portal or platform roles. A new email gets an INTERNA account with no usable password and the 72 h activation link; an existing internal user only gets the role plus a notice without link; a portal account's email is refused. Deactivation requires a motive (RN-004) and nobody can deactivate their own admin_cliente role. An admin of several organizations invites into the first one (`organizacion_con_permiso`); an organization selector waits for director P7. Scope by installation is NOT offered until T3 enforces it (showing it would promise a control that does not exist).

- S8 — Daily job and notifications (T5). Requirements: "RF-033 Alertar antes del vencimiento mediante umbrales configurables." "RF-060 Enviar alertas por vencimiento, observación, aprobación, rechazo y suspensión." "RF-061 Evitar duplicados mediante plantillas, preferencias e idempotencia." "Un trabajo programado evalúa vigencias diariamente. Las alertas se agrupan para evitar saturación." Implementation: (a) the beat entry runs at a fixed hour (crontab, default 06:00 America/Guayaquil, env `SIGECOP_JOB_DIARIO_HORA`); (b) an approved requirement whose current document expires within a threshold of `SIGECOP_DIAS_AVISO_VENCIMIENTO` (default 30,7) gets ONE pre-expiry alert per threshold crossed (the smallest threshold that covers the remaining days), never duplicated by re-runs; (c) once per organization and day, users with the new matrix action `recibir_resumen_alertas` (admin_cliente only until director P21) receive one email digest of the alerts created that day; no alerts → no email; a re-run the same day sends nothing. Who else receives notifications and the threshold values are director decisions (P21).

- S9 — Document inbox like the previous system (T6). Previous system (screenshot "Documentos" inbox): row checkbox for bulk selection, "Gestión" (Nuevo/Actualización), editable "Fecha emisión", "Fecha de caducidad", Aprobar/Rechazar. Requirements: "RF-032 Aprobar, observar o rechazar con motivo, evidencia y notificación." "RN-001 Ningún archivo aprobado se sobrescribe". Implementation: the inbox lists the current document of each requirement EN_REVISION with Gestión (version 1 = Nuevo, later = Actualización), upload date and expiry; users with `revisar_documentos` get row checkboxes, an optional emission date per row and bulk Approve / Observe / Reject (observe and reject require one shared comment). A bulk decision is all-or-nothing, creates one Revision + one audit event per document, and only accepts current documents whose requirement is EN_REVISION in organizations where the user has `revisar_documentos`. The emission date is stored on the Revision (documents are immutable), cannot be in the future nor after the document expiry. The single-document review form also accepts it.

- S10 — Reports (T8). Previous system "Informes": "Documentos Trabajadores" (Código, Cédula, Trabajador, Empresa, Nombre documento, Estado, Fecha emisión, Fecha caducidad) and "Información Trabajadores" (Cédula, Trabajador, Estado, Estado de documentos, Fecha nacimiento, RUC, Contratista, Posición, Correo, Teléfono...), each with company/date filters, keyword search, "Descargar a Excel". Requirements: "RF-063 Exportar información autorizada con fecha, filtros y trazabilidad." "RN-009 Las exportaciones sensibles requieren autorización, finalidad y auditoría." Implementation: new app `apps/reportes` (last in the dependency chain because it reads every domain app). Viewing a report needs `ver_registros`; the Excel export needs `exportar_reportes` and is audited with `ExportacionAuditoria` (filters, rows, SHA-256) plus an `EXPORTAR_<REPORTE>` event. "Información de trabajadores" shows enablement (Sí/No from `calcular_habilitacion`) and NEVER the antecedentes result (constitution §2.7), unlike the previous system; the antecedentes report waits for director P15.

- S11 — Person file (T13). Diagnosis (§2 and §6 day 13): "Faltan campos del sistema anterior (nacionalidad, domicilio, teléfono de emergencia, posición) y expediente cronológico (RF-023)." Acceptance: "La línea de tiempo muestra documentos, permisos, verificaciones (sin resultado) y accesos". Implementation: (a) Persona gets optional `nacionalidad`, `domicilio`, `telefono_emergencia`, editable in the person form and shown in the "Información de trabajadores" report; "posición" already exists per company as `Asignacion.cargo_o_actividad` (no new field). (b) The chronological file lives in `apps/reportes` (the only app allowed to read every domain app) at `reportes/personas/<id>/expediente/`, needs `ver_registros` (garita gets 403, constitution §2.7), is filtered by the user's organizations (another organization's person → 404) and lists, newest first: assignments, document uploads, document reviews, entry permits, antecedentes verifications and gate events. Verifications show ONLY that a verification exists, its date and "En curso"/"Cerrada" — never `resultado`, the detailed state, the certificate or `vigente_hasta`. Read-only: it writes nothing.

- S12 — Entry reports (T9). Plan day 9: "Reportes: solicitudes de ingreso e histórico de ingresos a planta" — acceptance: "Filtros por contratista, planta, estado y fechas". Previous system "Procesos → Solicitud de ingreso": "filtros por contratista, planta, estado y fechas; paginado". Implementation: two more reports in `apps/reportes` with the S10 rules (`ver_registros` to view, `exportar_reportes` for the audited Excel, garita 403). "Solicitudes de ingreso": one row per entry permit (requested date, ID, worker, company, plant, state, validity, approver), filters company, plant, state and requested-date range. "Histórico de accesos": one row per gate event (date and time, ID, worker, company, plant, type Entrada/Salida/Denegado, denial reason, registered by), filters company, plant, type and date range. Dates are local (America/Guayaquil). Permits keep the current states; T4 (human approval) will add its state without changing the report.

- S13 — Assisted judicial antecedentes (T12, session 2). Plan day 12: "Antecedentes judiciales asistidos (MVP 5.5)" — acceptance: "Un hallazgo siempre pasa a revisión; un fallo nunca es favorable". Constitution: never bypass a CAPTCHA or antibot controls; four eyes; immutability.
- S14 — Closing (T14). Plan day 14: "Verificación independiente, corrección de errores, actualización de la constitución, guía de prueba manual" — acceptance: "Suite verde, checklist de aceptación AC-001..AC-010". The constitution must describe what T1-T13 changed (permission matrix, internal users, daily job and digest, local date, bulk review, reports and person file, assisted judicial evidence) and the open director questions, without contradicting existing rules silently.
